# Requerimientos funcionales

Los requerimientos funcionales definen los resultados y operaciones observables que debe proporcionar el sistema para administrar inscripciones académicas de una sola universidad. Se organizan por capacidades y utilizan identificadores estables, independientes de nombres de clases, rutas HTTP y estructuras de almacenamiento.

Cada criterio de aceptación expresa una condición comprobable. Las restricciones de dominio se formalizan en el modelado; aquí se identifican las obligaciones funcionales sin duplicar toda su especificación.

La combinación de tipo y número de documento personal conserva su unicidad global y no puede reutilizarse; las bajas se rechazan cuando subsisten dependencias vigentes incompatibles. |
| RF-009 | El sistema debe consultar los tipos de documento de identidad admitidos mediante un catálogo institucional fijo.                                                                                                                   | Las identidades utilizan tipos reconocidos sin habilitar modificaciones arbitrarias del catálogo desde la API.                                                                                                                                                                                                                                                                  |

## 2. Periodos y ofertas de cursos

| ID     | Requerimiento                                                                                                                                                                       | Criterio de aceptación                                                                                                                                                                                                                                                                                                                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RF-010 | El sistema debe registrar y consultar periodos académicos y permitir corregir su nombre, código, fechas académicas y ventana de inscripción únicamente mientras estén en `PLANNED`. | Los cambios respetan la unicidad operativa, la coherencia temporal y los compromisos académicos confirmados; en otros estados no se admite edición ordinaria de esos atributos.                                                                                                                                                                                                                             |
| RF-011 | El sistema debe permitir transiciones autorizadas del ciclo de vida de los periodos académicos.                                                                                     | La apertura, el desarrollo, el cierre y la cancelación respetan las condiciones vigentes del periodo.                                                                                                                                                                                                                                                                                                       |
| RF-012 | El sistema debe registrar, consultar y configurar ofertas de cursos vinculadas a un curso, un periodo, una sección, un docente y una capacidad máxima.                              | Curso y periodo no se modifican tras la creación; la sección solo se corrige en `DRAFT`; docente y capacidad se ajustan en `DRAFT`, `OPEN` o `CLOSED` bajo las restricciones de integridad, habilitación y trazabilidad.                                                                                                                                                                                    |
| RF-013 | El sistema debe permitir las transiciones autorizadas de ofertas de cursos, incluidas apertura, cierre, reapertura y cancelación.                                                   | Tanto la apertura inicial como la reapertura requieren docente `ACTIVE` habilitado, capacidad consistente, periodo `OPEN` antes del inicio académico o `IN_PROGRESS` desde ese inicio y fecha institucional dentro de la ventana de inscripción, con ambos límites inclusive. Un periodo `OPEN` atrasado no permite abrir ni reabrir ofertas. Ninguna transición modifica implícitamente sus inscripciones. |
| RF-014 | El sistema debe mostrar la ocupación y los cupos disponibles de las ofertas según las inscripciones que conservan plaza.                                                            | La capacidad disponible refleja los movimientos vigentes y nunca resulta negativa ni supera la capacidad máxima.                                                                                                                                                                                                                                                                                            |
| RF-015 | El sistema debe impedir nuevas operaciones ordinarias de inscripción cuando el periodo o la oferta no las admita.                                                                   | Una oferta existente no basta para autorizar inscripciones si su situación o la del periodo es incompatible.                                                                                                                                                                                                                                                                                                |

## 3. Inscripciones y movimientos

| ID     | Requerimiento                                                                                                                                            | Criterio de aceptación                                                                                                                                                                                                                                         |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RF-016 | El sistema debe registrar directamente una inscripción válida en una oferta, sin etapa previa de solicitud o aprobación.                                 | Una operación aceptada crea una inscripción `ENROLLED` y una rechazada no crea una inscripción parcial.                                                                                                                                                        |
| RF-017 | El sistema debe verificar la habilitación del estudiante y la asociación vigente del curso con su programa académico.                                    | Se rechaza la inscripción de estudiantes no activos o en cursos no asociados a su programa académico.                                                                                                                                                          |
| RF-018 | El sistema debe comprobar conjuntamente la ventana de inscripción, el estado del periodo, la disponibilidad de la oferta y los cupos.                    | Una inscripción solo se acepta si todas esas condiciones se cumplen en el momento de registrarla.                                                                                                                                                              |
| RF-019 | El sistema debe impedir más de una inscripción vigente de un estudiante en un mismo curso y periodo, incluso si se intenta utilizar otra sección.        | Los intentos repetidos o sobre distintas secciones no generan duplicidad vigente.                                                                                                                                                                              |
| RF-020 | El sistema debe mantener la unicidad y la ocupación de cupos frente a solicitudes simultáneas.                                                           | La concurrencia no produce sobrecupos, duplicidades ni movimientos registrados a medias.                                                                                                                                                                       |
| RF-021 | El sistema debe permitir cancelar una inscripción vigente conforme al momento académico permitido.                                                       | La cancelación ordinaria requiere una inscripción `ENROLLED`, un periodo en `OPEN` y una fecha anterior al inicio académico; deja la inscripción en `CANCELLED` y libera su cupo. Una anulación posterior requiere intervención administrativa extraordinaria. |
| RF-022 | El sistema debe permitir el retiro de una inscripción vigente durante el periodo académico en curso.                                                     | El retiro válido registra `WITHDRAWN`, libera cupo y no habilita una reinscripción ordinaria al mismo curso y periodo.                                                                                                                                         |
| RF-023 | El sistema debe permitir cambiar de sección una inscripción vigente dentro de la ventana habilitada.                                                     | El cambio conserva la identidad de la inscripción, exige el mismo curso y periodo, verifica cupo en el destino y traslada la ocupación sin resultados intermedios visibles.                                                                                    |
| RF-024 | El sistema debe permitir correcciones administrativas extraordinarias sujetas a autorización y justificación específicas.                                | Solo personal con autorización de corrección puede efectuarlas, sin alterar arbitrariamente información ajena ni vulnerar la integridad del registro.                                                                                                          |
| RF-025 | El sistema debe conservar un historial inalterable de movimientos relevantes de cada inscripción.                                                        | Se puede reconstruir su creación, cancelaciones, retiros, cambios de sección y correcciones, con responsable, momento, motivo exigible y datos modificados.                                                                                                    |
| RF-026 | El sistema debe gestionar la reinscripción posterior a una cancelación mediante un registro nuevo cuando las condiciones ordinarias vuelvan a cumplirse. | La inscripción cancelada permanece histórica y la nueva inscripción no sobrescribe la anterior.                                                                                                                                                                |
| RF-027 | El sistema debe conservar el estado final registrado de cada inscripción cuando se cierre el periodo académico.                                          | El cierre no convierte automáticamente las inscripciones en completadas o aprobadas ni reemplaza sus estados.                                                                                                                                                  |
| RF-028 | El sistema debe exigir una justificación para cancelaciones, retiros, cambios de sección y correcciones.                                                 | Ninguna de esas operaciones se completa sin motivo; la inscripción inicial ordinaria no lo requiere.                                                                                                                                                           |
| RF-029 | El sistema debe ofrecer consultas de inscripciones vigentes e históricas y de sus movimientos.                                                           | Puede distinguirse una inscripción `ENROLLED`, `CANCELLED` o `WITHDRAWN` y recuperar su trayectoria sin restaurar registros cerrados.                                                                                                                          |

| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RF-030 | El sistema debe importar estudiantes desde archivos CSV y XLSX aplicando las mismas reglas de interpretación de datos y validación, independientemente del formato de origen. | Los datos equivalentes producen resultados equivalentes de aceptación, rechazo y detección de duplicados. | RF-036 | El sistema debe conservar el archivo original y un resultado verificable de cada importación admitida.                                                                        | Quedan disponibles su origen, responsable, cantidades por resultado y observaciones por fila.                                                                                                                                                                                                              |

## 6. Usuarios, sesiones y autorizaciones

| ID     | Requerimiento                                                                                                                                                                                                                                                                 | Criterio de aceptación                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

| RF-042 | El sistema debe permitir registrar y consultar cuentas internas, crear una cuenta junto con una persona, vincular posteriormente una persona existente a una cuenta sin vinculación y cambiar administrativamente el estado de las cuentas conforme a la autoridad del actor. | Una cuenta puede crearse sin persona o asociarse a una persona existente, vigente y libre de otra cuenta; la creación conjunta de persona y cuenta se confirma indivisiblemente. La vinculación posterior exige una cuenta sin persona asociada, una persona existente y vigente no vinculada a otra cuenta, autorización y evidencia; una asociación establecida no admite reasignación ni desvinculación ordinaria. | RF-046 | El sistema debe permitir consultar roles y asignaciones vigentes, y administrar asignaciones de acuerdo con los permisos y las restricciones del destinatario.                                                                                                                | Una cuenta puede reunir varios roles sin herencia; sus permisos efectivos son la unión de los permisos vigentes. ## Operaciones funcionales por recurso

La creación, la consulta, la modificación, la baja lógica y las transiciones de estado son capacidades diferentes. Cada recurso dispone únicamente de las operaciones indicadas; la existencia de una tabla, un atributo de baja lógica o un módulo no habilita operaciones adicionales.

| Recurso                                          | Operaciones incluidas                                                                                                                                                                                       |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Personas                                         | Registrar, consultar y actualizar datos personales no documentales; conservar inmutables el tipo y número de documento registrados.                                                                         |
| Estudiantes                                      | Registrar, consultar, actualizar el perfil y efectuar transiciones autorizadas de estado.                                                                                                                   |
| Docentes                                         | Registrar, consultar, actualizar el perfil y efectuar transiciones autorizadas de estado sin dejar obligaciones docentes desatendidas.                                                                      |
| Facultades, departamentos y programas académicos | Registrar, consultar, actualizar y dar de baja lógicamente cuando las dependencias vigentes lo permitan.                                                                                                    |
| Cursos                                           | Registrar, consultar, actualizar y dar de baja lógicamente cuando las dependencias vigentes lo permitan.                                                                                                    |
| Categorías de cursos y tipos de documento        | Consultar y utilizar los catálogos institucionales establecidos.                                                                                                                                            |
| Asociaciones programa–curso                      | Habilitar, consultar y cerrar episodios de vigencia; conservar los antecedentes.                                                                                                                            |
| Periodos académicos                              | Registrar y consultar; corregir nombre, código, fechas y ventanas únicamente en `PLANNED`, y efectuar las transiciones definidas.                                                                           |
| Ofertas de cursos                                | Registrar, consultar y modificar atributos permitidos según su estado, además de efectuar las transiciones definidas.                                                                                       |
| Inscripciones                                    | Registrar, consultar, cancelar, retirar, cambiar de sección y corregir extraordinariamente con autorización específica.                                                                                     |
| Movimientos de inscripción                       | Registrar como consecuencia de operaciones admitidas y consultar; no modificar ni eliminar antecedentes.                                                                                                    |
| Cuentas internas                                 | Registrar cuentas con o sin persona existente, crear persona y cuenta conjuntamente, vincular una persona posteriormente, consultar cuentas y cambiar su estado; sin actualización genérica ni eliminación. |
| Roles                                            | Consultar roles y asignaciones, administrar asignaciones permitidas y crear o actualizar roles personalizados; se protegen los roles y asignaciones institucionales.                                        |
| Permisos                                         | Consultar y utilizar el catálogo establecido; no crear ni alterar permisos arbitrariamente.                                                                                                                 |
| Sesiones                                         | Iniciar, renovar y revocar accesos mediante sus operaciones propias.                                                                                                                                        |
| Importaciones de estudiantes                     | Admitir archivos, consultar progreso, resultados y evidencia autorizada.                                                                                                                                    |
| Reportes y auditoría                             | Consultar información autorizada; los eventos de auditoría se incorporan como evidencia y no admiten edición ni eliminación ordinaria.                                                                      |

No se incluye una operación general de restauración de registros eliminados, eliminación física ni edición irrestricta de entidades. Los estados funcionales y las operaciones extraordinarias conservan sus reglas particulares.

## Límites funcionales

Los requerimientos no incluyen aprobación de solicitudes de inscripción, listas de espera, autoservicio estudiantil o docente, calificaciones, prerrequisitos, horarios, asistencia, pagos, notificaciones, sincronización institucional automática ni una plataforma general de análisis o exportaciones. La gestión de datos académicos, cuentas y consultas permanece subordinada al proceso de inscripción y a su supervisión.

La numeración `RF` identifica obligaciones estables del producto; no equivale a una secuencia de desarrollo ni a nombres de funcionalidades implementadas.
